# 浏览器自称与真实平台自洽，不冒充手机

承接 [`0002`](0002-本机探针与浏览器取参的取舍.md) 的决定 1（真 Chrome + chromedp 取参）：
本 ADR 只管**自称**——浏览器向阿里云风控报告自己是台什么设备——并**不改**
0002 的任何结论（本机失败仍是弱证据、冲突时以手机端为准）。

## 背景

`har#4`（本轮真实窗口：探针 + 手机两条链路）里唯一能看见的硬缺陷是探针的
环境自称自相矛盾：

```text
user-agent:          … HeadlessChrome/153.0.0.0 Safari/537.36
sec-ch-ua-platform:  "macOS"          sec-ch-ua-mobile: ?0
window.innerWidth:   500   screen.width:  800   dpr: 1
```

即：一次参数铸造（`InitCaptcha`）与两次设备指纹上报（cloudauth-device 的
Log2/Log3）都在告诉阿里云「headless 桌面 Chrome，800×600 屏」，而窗口尺寸是手机尺寸
（视口 500×789 比屏幕 600 还高，物理上不可能）。阿里云把这类组合点名过：
`F009`「检测到虚拟设备环境（…、模拟器、桌面浏览器模拟移动设备）」。

同时必须承认：`har#3` 里**一台真桌面 Edge 也先吃过一次 F001 才成功**，
所以环境自称的缺陷**不是已证的充分原因**（F001 的官方定义只是「疑似攻击请求，
风险策略不通过」）。本决定只做「去掉能看见的自相矛盾」，不宣称因果。

另一个诱因是移动端：手机那条权威成功样本（T001）用的是钉钉 webview 的 Android UA，
看上去「冒充手机」很有吸引力。

## 决定

1. **默认自称一台真实的桌面 Chrome**：UA 取自本机 Chrome 的真实 UA 去掉
   `HeadlessChrome` 的标记，客户端提示（`Sec-CH-UA*`）沿用真实值，屏幕改成这台机器
   真实的内建屏尺寸（1280×832 @2x），视口保持原状，**不打开触摸**。
   理由：桌面自称几乎不需要撒谎——WebGL 依旧如实报 Apple M4、locale/时区/硬件并发
   都是真的；而冒充手机会同时与这些硬件指纹**矛盾**，正好落在 `F009`
   「桌面浏览器模拟移动设备」的定义里。
2. **四者必须一起换**：UA 字符串、`Sec-CH-UA*`、屏幕几何、触摸能力。
   只改 UA 字符串会让 Chrome **停发全部 `Sec-CH-UA-*`**（本机实测；见
   `internal/chromecaptcha/presentation.go` 的注释）——那是把一个矛盾换成另一个更显眼的。
   所以「换自称」= `Emulation.setUserAgentOverride` **带** `userAgentMetadata`
   + `Emulation.setDeviceMetricsOverride`（+ 手机档的 `setTouchEmulationEnabled`）。
3. **手机自称保留为显式选项，不作默认**：`--mobile`（或直接给 `--ua` 粘钉钉那串 +
   `--mobile`）留给实验；默认永远是桌面。理由同 1，且它能在一处翻开关，不必改代码。
4. **预热要等设备指纹上传落地再宣布「可以点了」**：`deviceToken` 铸在 SDK 初始化那一刻，
   而设备指纹数据（Log2/Log3）随后才上传（实测相隔 0.49s / 3.42s 才发完）。
   这一步发生在 **T0 之前**，不占窗口预算，只是把确定能避免的竞态去掉。
   ⚠️ 它**不是**已证的 F001 成因，只是「没有理由不等」。
   ⚠️ 它**也不改** `deviceToken` 本身的铸造时刻：那发生在 `initAliyunCaptcha` 内部，
   我们只能在「它把实例交回来」之后才开始等（`har#4` 里 token 的嵌入时间戳就在 +0.18s）。
   所以「三次尝试携带的是同一份可能没收集完的设备载荷」这个疑问（`har#4` 复盘 §7）
   仍然没被回答 —— 要回答它得另做离线实验（页面新起 vs 静置 10s 后首次点击，比载荷段长度）。
5. **HTTP 客户端默认保持项目自报名**（`hdufuck/skl (+…)`）：承载 `captchaVerifyParam`
   的那条请求默认不改身份。想对齐浏览器自称时用 `--client-ua browser`
   （库侧 `skl.WithUserAgent` / `SetUserAgent`）——这是显式选择，不是默认行为。

## Considered Options

- **仿手机端钉钉那串 UA（把桌面 Chrome 装成钉钉 webview）**：否决作默认。
  `Version/4.0 Chrome/100.0.4896.58 UWS/…` 与真实的 JS 引擎（Chrome 153）对不上，
  硬件指纹（Apple M4 GPU）也对不上，且在 `F009` 的字面定义里。
- **用 Pixel / Galaxy 这类「通用」移动 UA**：否决。那是所有移动端模拟器的默认型号，
  反而是个特征；`--mobile` 内置模板用的是成功样本里那台真机的型号（2211133G）。
- **只覆盖 UA 字符串**：否决。实测会让 `Sec-CH-UA-*` 整批消失。
- **把窗口也缩成手机尺寸**：无证据支持，且 headless 下 `window-size` 与
  `screen` 本来就不同源；本决定只把 `screen` 换成真实值，不动窗口。
- **不等设备指纹上传**：否决。等待发生在 T0 之前，零成本。

## Consequences

- **F001 的归因仍不可区分**：本决定去掉了环境自称里的矛盾，但 `har#3` 的反例说明
  真桌面浏览器也会被拒一次。窗口内的判据只能是「换新参数重试后是否 T001」，
  不得写成「F001 = 指纹问题」。
- **预制模板里的机型串**（`2211133G` / Android 13）来自成功样本那台手机；它是公开机型串，
  不指向个人，但不想用就用 `--ua` 自己给一串。
- **移动端自称永远只能当实验档**：桌面 Chrome 冒充手机的硬件指纹矛盾无法消除。
- 每次动自称（或升级 Chrome）都要重跑 `internal/chromecaptcha` 的离线护栏
  （`TestDesktopSelfPresentationHasNoHeadlessFingerprint` / `TestMobileSelfPresentation`）
  与真·取参体检（`go test -tags integration ./internal/chromecaptcha/`）。
- 自称只在 `internal/chromecaptcha` 一处，且默认值写在 `presentation.go` 的常量里；
  换机器（屏幕尺寸不同）时改那一处即可。
