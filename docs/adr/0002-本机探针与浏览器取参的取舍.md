# 以「库可用性」为目标的探针允许从本机发出，并以浏览器官方 SDK 取参

取代 [`0001`](0001-证据只能来自一次真实签到窗口.md) 的决定 1 与决定 2；
**保留**其决定 3（探针按信息量/副作用排序）与决定 4（遗留端点只作单边证据）；
决定 3 里的「首个写入即停」与写入闸门已整体移除，见下决定 4。

## 背景

0001 的目标是**干净归因**：判定「服务端在写入考勤之前是否要求一次通过校验的
`CaptchaVerifyParam`」。为此它规定唯一采集器是真机钉钉 webview + 抓包代理，
且所有探针都在手机端改包重放，避免把客户端指纹与网络来源差异引进结论。

现在的目标变了：要**一次窗口内同时回答**「是否强制」并**验证本库
（`hdufuck/skl`）的签到封装路径是否可用**。后者的主体只能是本机 Go 客户端——
手机端改包重放永远无法证明库里的 `SignIn` / `SignInLegacy` / `SignInLegacyAnalyze`
能不能跑通。同时 `CaptchaVerifyParam` 只能由客户端 JS 生成（阿里云没有 Go 客户端
生成 SDK），因此还需要一次浏览器自动化来产出真值。

## 决定

1. **探针允许从本机 Go 客户端发出**，并引入真 Chrome（chromedp）驱动官方 SDK 取参。
   模拟器/容器化 Android 仍然排除——这是不可回落的底线。
2. **证据分级随目标分化**：
   - **库可用性**：本机探针的结论是强的（成功就是成功）。
   - **`CaptchaEnforcement` 归因**：本机探针的**失败**是弱的——客户端指纹、出口 IP、
     WAF 都可能是原因，而非服务端策略。只有「未携带真凭证却写入了记录」
     「响应体明确指向人机层/参数层」两类观测算强证据。
3. **冲突时以真机为准**：若本机探针与手机端官方客户端的结论冲突，
   以手机端为准。手机端那条铁证由 Reqable 上报服务器并入同一份报告。
4. **0001 的决定 3、4 继续生效**：探针按「不需要人机 → 需要人机」排序；
   其中「首个写入即停」的写入闸门已**整体移除** —— 探针不再判读、不再因
   写入而停，每档请求之后只把当时的今日考勤记录原样记进报告，由人判断
   （一次真实窗口的代价太高，先把请求和记录拿全）。遗留端点的失败仍不可解释。

## Considered Options

- **坚持 0001：所有探针都在手机端改包重放**：否决。它无法验证库的封装路径，
  而这正是本次窗口的主要目的；且手机端 Reqable **不提供**断点/脚本/重写
  （官方以防止滥用为由禁用），改包重放本身很笨重。
- **在 Go 里重实现阿里云验证码协议**：否决。参数由阿里云侧签名、与场景和域名绑定，
  且算法会轮换；`captcha.go` 早已把这条排除。
- **用安卓模拟器/容器**：否决（沿用 0001）。设备指纹与真机不同，且引入无法归因的变量。
- **用 playwright-go 而非 chromedp**：否决。运行时仍依赖 Node 驱动，
  对本任务（hook 一个 JS 回调）没有额外收益；chromedp 纯 Go、
  `CGO_ENABLED=0` 可编译、只依赖系统已装 Chrome。

## Consequences

- 本机探针的失败**不得**单独用于判定「服务端强制人机验证」；报告必须把它标为弱证据，
  并与手机端结论交叉。这是为「一次窗口同时验证库可用性」付出的代价。
- 引入两个新东西需要在窗口前预置并演练：浏览器预热（chromedp + 真 Chrome）、
  手机 Reqable 上报服务器（需一个免费账号）。预置清单见
  [`../signin-probe.md`](../signin-probe.md) 第 4.1 节。
- 归一化的落盘仍遵守 0001 的纪律：不提交任何 HAR，只保留「如何获取」；
  `probe-results/` 与 `*.har` 一并 gitignore，只提交人工脱敏后的 markdown 片段。
- 0001 关于「实验不可重复、必须显式记录未证明项」的后果继续成立。
